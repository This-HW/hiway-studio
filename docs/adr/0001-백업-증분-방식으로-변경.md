# ADR-0001: 백업을 매일 전체 스냅샷에서 증분 방식으로 변경

## 상태
승인 (HW가 2026-09-30에 "[가정] #14 백업" 검토 중 제안·확정)

## 배경
기존 `[가정]` #14는 "projects/ 전체 + pg_dump를 1일 1회 백업, 7일 보관"이었다.
영상 산출물이 쌓이면 매일 전체 스냅샷의 용량이 기하급수적으로 증가한다.

## 결정
- **파일** (`projects/`, `library/`): 매일 rsync `--link-dest` 하드링크 스냅샷, 30세대 보관.
  매일 "전체처럼 보이는" 디렉토리가 생기지만, 변경되지 않은 파일은 하드링크로 공유되므로
  실제 디스크 사용량 ≈ full 1개 + 30일간 신규 파일분.
- **DB**: `pg_dump` 매일 1회, 14일 보관 (메타데이터만이라 용량 작음).
- 복원 절차를 `infra/scripts/restore.sh`와 문서로 함께 제공한다 (백업만 있고 복원 테스트가 없으면 무용지물).

## 근거
- 산출물 불변 규칙(ARCHITECTURE §8, files/immutability.py): 성공한 파일은 덮어쓰지 않으므로,
  증분 체인이 깨질 원인(수정된 파일의 버전 추적)이 원천적으로 없다.
- tar 증분 체인보다 하드링크 스냅샷이 복원이 단순하다 (그냥 디렉토리 복사).
  1인 운용 + OSS 공개를 고려하면 외부 도구(borg/restic) 의존 없는 rsync 방식이 낫다.
- DB 덤프는 매일 전체여도 수 MB 수준이라 문제없다.

## 영향
- 코드: `infra/scripts/backup.sh`, `infra/scripts/restore.sh` 신규 (Phase 0).
- 문서: PROJECT_ARCHITECTURE §13 #14 행을 본 결정으로 교체.
  시스템 설계서 §13.3("1일 1회 전체 백업, 7일 보관")은 본 ADR로 대체(superseded)된다.
- 보관 정책: 기존 7일 → 파일 30세대 / DB 14일로 변경.

## 관련
- 시스템 설계서 §13.3, §11.3 (불변성), PROJECT_ARCHITECTURE §13 #14
