# ADR-0013: 잡 실행 소유권(claim·lease)과 지속 복구(reconcile)

## 상태
제안

## 배경
감사(audit roadmap, 계획 `docs/plans/2026-11-09-audit-roadmap-fixes/plan.md` §G8 F02·F03·F05·P24·H2·P20·H1·RH1)에서
워커 잡 수명주기의 결함이 확인됐다.

- 워커가 잡 전체를 `session_scope()` 트랜잭션 하나로 돌렸다. 실패 분기에서 `failed`·재시도 카운터를 기록한 뒤
  `raise`/`self.retry`하면 전부 롤백돼 행이 `queued`로 남았다(F02/F03).
- `retry_job`이 job_type과 상관없이 `q.image.run_generation`만 보냈고(F05), `cancel_job`은 Generation만 바꿔
  Video `generating`·Shot `video_generating`이 그대로 남았다(P24).
- `task_acks_late=True`로 재전달은 되지만, 워커는 `succeeded` 행도 provider에 다시 제출했다(P20).
  행 소유권 개념이 없어 같은 메시지가 두 번 오면 두 실행이 동시에 쓰고, 만료된 실행이 나중에 성공을 덮을 수 있었다(H2 ABA).
- `dispatch_after_commit`은 콜백 하나가 예외를 내면 나머지를 잃었다. 브로커가 잃은 잡을 되살리는 장치(reconcile)가 없었다(H1).
- provider submit 응답이 유실되면(ReadTimeout 등) 재시도가 같은 작업을 다시 제출해 비용이 중복될 수 있었다(RH1).

## 결정
D4·D7을 다음과 같이 구현한다. 대상은 `generations`와 `audio_generations`다(타임라인 렌더는 B4b, P1 오케스트레이션은 D9).

1. **실행 필드**: `exec_token`(UUID), `lease_expires_at`, `heartbeat_at`, `submit_state`(`none|intent|submitted`),
   `dispatched_at`. audio에는 `provider_job_id`·`retry_count`·`attempt_count`를 추가한다(Alembic `0012_job_execution`).
2. **claim**: 태스크 시작 시 조건부 UPDATE 한 번(`status='queued' → 'running'`, 새 토큰, lease = now + `LEASE_TTL_SEC`)을
   짧은 트랜잭션으로 commit한다. 0행이면 no-op으로 반환하고 메시지는 ACK된다. generation은 같은 트랜잭션에서
   `generation_attempts` 행을 연다.
3. **guarded write**: 이후 모든 쓰기(진행률, heartbeat, submit_state, 성공, 실패, 종속 Shot/Video/배치 부모 갱신)는
   `id + exec_token + status='running'` 조건부 UPDATE로 시작하는 짧은 트랜잭션이다. 0행이면 작업을 멈추고 아무것도
   게시하지 않는다. 이미 쓴 파일은 고아로 남는다. provider 폴링 동안 DB 트랜잭션을 열어두지 않는다.
   백그라운드 heartbeat가 `HEARTBEAT_INTERVAL_SEC`마다 lease를 연장한다.
4. **submit intent(D7)**: `adapter.submit` **전에** `submit_state='intent'`를 commit하고, provider ID를 받으면
   `submitted`+ID를 commit한다. intent 이후 결과가 불확실한 실패(응답 유실·ReadTimeout·폴링 중단·다운로드 실패·
   intent 후 크래시)는 `failed` + `PROVIDER_UNCERTAIN`이고 **자동 재제출하지 않는다**(self.retry·재전달·reconcile 모두).
   intent 이전 실패와 "확실히 전송 전" 실패(httpx `ConnectError`/`ConnectTimeout`/`PoolTimeout`/`ProxyError`/
   `UnsupportedProtocol`, 또는 네트워크 원인 없는 확정 거절 코드 `RATE_LIMITED`·`MODEL_UNAVAILABLE` 등)만
   기존 재시도 정책(지수 백오프, 최대 `RETRY_MAX_ATTEMPTS`)을 따른다. provider가 최종 실패를 보고한 경우는 결과가 확정이므로
   그 오류 코드로 `failed`가 되지만, provider 잡이 존재했으므로 역시 자동 재제출하지 않는다.
5. **실패 영속**: 실패·재시도 기록은 raise 전에 commit한다. SSE `job.failed`는 commit 뒤에만 보낸다.
6. **dispatch 견고성**: `dispatch_after_commit`은 콜백이 예외를 내도 나머지를 모두 시도하고 로그를 남긴다.
   놓친 전송은 reconcile이 복구한다.
7. **retry/cancel**: `job_execution.JOB_TASKS`(job_type → 태스크·대상 ID)로 태스크를 고른다. retry는 `failed`에서만
   허용하고 실행 필드를 비우며 종속 행(Video `generating`, Shot `video_generating`/`frame_generating`, LoRA `training`,
   배치 부모)을 되돌린다. `PROVIDER_UNCERTAIN` 시도의 `generation_attempts` 행은 지우지 않고 새 시도를 연다
   (예산 예약은 B5가 D1/D7에 따라 연결, 코드에 TODO 표시). cancel은 Video/Shot(및 연결된 audio 행)으로 전파하고
   `exec_token`을 비워 실행 중 워커의 다음 쓰기를 0행으로 만든다. 워커는 그 시점에 `adapter.cancel`을 best-effort로 호출한다.
8. **reconcile(H1)**: `job_recovery.reconcile_once(now)`
   - (a) lease가 만료된 `running`: `submit_state`가 intent/submitted면 `failed`+`PROVIDER_UNCERTAIN`(재전송 없음),
     `none`이면 `queued`로 되돌리고(토큰 제거, `retry_count+1`) 재전송. 자동 재시도 예산을 다 쓴 행은 `failed`.
   - (b) `RECONCILE_REDISPATCH_AFTER_SEC` 동안 재전송되지 않은 `queued` 행은 한 번 재전송(`dispatched_at` 기준).
   - (c) `RECONCILE_P1_STUCK_AFTER_SEC`가 지나도 `queued`인 P1 원장(lora_train/style_extract)은 `failed`.
   - 구동: API lifespan의 asyncio 루프가 `RECONCILE_INTERVAL_SEC`마다 스레드에서 실행한다(시작을 막지 않음, 예외는 로그 후
     다음 주기). 워커 `worker_ready` 신호에서 1회 보조 실행. `RECONCILE_ENABLED` 환경변수로 끄고 켠다.
     미설정이면 켜짐, 단 `SSE_BACKEND=memory`(테스트·데모)이면 꺼짐.
9. **Celery**: `task_acks_late=True`에 `task_reject_on_worker_lost=True`를 더한다.

### ACK/재전달 결정표

| 메시지가 도착했을 때 행 상태 | 워커 동작 | provider 호출 | 메시지 |
|---|---|---|---|
| `queued` | claim 성공 → 실행 | 실행 중 1회(intent 후) | 완료 후 ACK |
| `queued`, 동시에 두 전달 | 한쪽만 claim, 다른 쪽 0행 no-op | 1회 | 둘 다 ACK |
| terminal(`succeeded`/`done`/`failed`/`canceled`) | claim 0행 → no-op | 0회 | ACK |
| `running`, lease 유효(살아 있는 중복) | claim 0행 → no-op | 0회(살아 있는 실행만 호출) | ACK |
| `running`, lease 만료 | 워커는 no-op. reconcile이 (a)에 따라 `queued`로 되돌려 재전송하거나 `PROVIDER_UNCERTAIN`으로 종료 | `submit_state=none`일 때만 재실행에서 1회 | ACK |
| 워커 프로세스 사망(OOM/SIGKILL) | `task_reject_on_worker_lost`로 재전달 → 위 표대로 판정 | 위와 같음 | 재전달 |

### Redis visibility_timeout과 잡 기한
Redis 브로커는 ACK되지 않은 메시지를 `visibility_timeout`(기본 1시간)이 지나면 다른 워커에 다시 준다. 폴링이
1시간을 넘는 잡(최대 `POLL_MAX_ITERATIONS` × `POLL_INTERVAL_MAX_SEC` ≈ 100분)은 실행 중에 중복 전달될 수 있다.
이 중복은 claim에서 0행 no-op이 되므로 provider 재호출이 없다. 따라서 `visibility_timeout`을 잡 기한보다 길게 맞출
필요는 없지만, 불필요한 재전달을 줄이려면 운영 설정에서 최장 잡 기한보다 크게 두는 것을 권한다. 잡 소유권의 정본은
브로커가 아니라 DB의 `exec_token`·lease다.

## 근거
- **토큰 + 허용 상태 조건(CAS)**: 상태만 보는 조건(`status='running'`)으로는 "A 만료 → reconcile 재큐 → B claim →
  A 늦은 성공"(ABA)을 막지 못한다. 실행마다 새 토큰을 발급하면 늦은 실행의 쓰기는 항상 0행이다.
- **짧은 트랜잭션**: 폴링 동안 트랜잭션을 열어두면 실패 기록이 롤백되고(F02), SQLite에서는 쓰기 잠금을 오래 잡는다.
  조건부 UPDATE를 첫 문장으로 두면 Postgres READ COMMITTED에서도 행 잠금 후 조건을 다시 평가하므로 두 실행 중 하나만 통과한다.
- **intent를 submit 전에 commit**: provider가 멱등 키를 보장하지 않으므로 "보냈는지 모름"을 DB에 남기는 것만이 자동 재제출을
  막는 방법이다. 보장 범위는 "시스템이 불확실 제출을 자동 재제출하지 않음"으로 한정한다(provider 측 중복 처리는 미검증).
- **reconcile을 API lifespan에**: 별도 beat/스케줄러 프로세스를 늘리지 않는다(큐·프로세스 최소화, ARCHITECTURE §8).
  worker_ready 보조 실행은 API가 내려가 있던 동안 잃은 잡을 워커 기동 시 회수한다.
- 버린 대안
  - Celery 결과 백엔드/`task_id` 기반 중복 제거: 브로커 상태에 의존하고, 재전달 시 task_id가 같아도 행 상태를 알 수 없다.
  - `SELECT ... FOR UPDATE`로 잡 전체 잠금: 폴링 동안 잠금을 쥐어야 해 F02와 같은 문제가 생기고 SQLite는 지원하지 않는다.
  - 업로드 등 submit 이전 단계 실패를 세밀하게 구분: 어댑터 계약(B7) 변경이 필요하다. 지금은 보수적으로 `intent` 이후
    네트워크 원인 실패를 불확실로 본다(어댑터 내부 업로드 단계의 ReadTimeout도 불확실로 분류된다).

## 추가 결정: 타임라인 렌더와 멀티샷 (B4b, 계획 D8·D9)

### 배경
- 렌더가 공용 이름(`output_new.mp4` → `output.mp4`, 이전 파일은 아카이브)과 공용 `_segments` 작업 폴더를 썼다. 두 실행이 겹치면
  서로의 파일을 덮거나 지웠고, 늦게 끝난 실행이 새 결과를 갈아치울 수 있었다(RH3 ABA).
- StudioError 경로는 `failed`를 flush한 뒤 raise해 롤백됐다. 타임라인이 `rendering`에 묶였다.
- `request_render`는 상태를 읽고 나서 `rendering`을 썼다(원자 claim 아님). 자막 큐·스타일 편집은 렌더 중에도 받아들여졌다(F13).
- 렌더 결과를 검증하지 않고 게시했다. 인코딩이 프리셋과 다르거나 자막이 투명·누락이어도 `done`이 됐다(H4).
- 같은 멀티샷 메시지가 두 번 오면 각 전달이 샷 6개·자식 잡 6개를 만들어 12개가 됐다(RH2).

### 결정
1. **렌더 claim**: `request_render`는 QC 게이트를 통과한 뒤 조건부 UPDATE 한 번으로 claim한다
   (`status != 'rendering'` 그리고 `content_version`이 QC가 본 값과 같을 것 → `rendering`, 새 `exec_token`, lease).
   0행이면 409 `RENDER_LOCKED`, 그사이 편집이 끼었으면 stale `QC_FAILED`. 컬럼: `timelines.exec_token`·`lease_expires_at`·
   `heartbeat_at`·`render_meta`(Alembic `0013_render_execution`).
2. **실행 시작**: 워커는 `heartbeat_at IS NULL`인 동안만 시작을 표시한다(토큰 유지, lease 연장). 중복·늦은 전달은 0행 no-op이다.
   렌더 중 백그라운드 heartbeat가 `HEARTBEAT_INTERVAL_SEC`마다 lease를 늘리고, ffmpeg 동안 DB 트랜잭션을 열어두지 않는다.
3. **시도별 파일**: 작업은 `timelines/<id>/attempts/<token>/`에서 한다. 자막 없는 중간본(concat)을 postflight 기준본으로 두고,
   최종본은 `timelines/<id>/output_<token 앞 8자>.mp4`로 하드링크한다(이미 있으면 거부, 하드링크 불가 시 배타 생성 복사).
   작업 폴더는 끝나면 지운다.
4. **postflight(D5/H4)**: `postflight_encoding` pass 필수. burn-in 트랙마다
   - 픽셀 존재 검사: 큐 중간 시점에 자막 밴드(`subtitle_band`)를 기준본과 비교해 휘도 차가 `RENDER_BURNIN_PIXEL_DELTA`보다 큰
     픽셀이 `RENDER_BURNIN_MIN_CHANGED_PX` 이상이어야 한다. 글리프 크기와 무관하게 투명·누락 자막을 잡는다.
   - OCR 검사: 렌더 높이 기준 글리프가 `RENDER_BURNIN_OCR_MIN_GLYPH_PX` 이상이면 `postflight_burnin`(기준본 포함)이 pass여야 한다.
   - **warn 처리**: OCR 엔진이 없어서 나온 warn(stub)과 OCR 하한보다 작은 글리프는 게시를 막지 않고 `render_meta.unverified`에
     사유를 남긴다. 그 밖의 warn(기준본 없는 미검증)과 모든 fail은 게시하지 않는다. 출력 끝 이후에 시작하는 큐는 렌더되지 않으므로
     검사에서 빼고 `unverified`에 개수를 남긴다.
5. **게시(D8)**: `UPDATE timelines SET output_path=<시도 파일>, status='done', render_meta=… WHERE id AND exec_token AND status='rendering'`
   한 번이 게시다. 0행이면 아무것도 바뀌지 않고 시도 파일은 참조 없는 고아로 남는다. `render.completed`는 commit 뒤에 보낸다.
6. **실패 영속**: StudioError와 예기치 않은 예외 모두 같은 토큰 조건으로 `failed`+오류를 짧은 트랜잭션으로 commit한 뒤 raise한다.
   이전 `output_path`는 그대로다. 태스크 래퍼의 안전망은 토큰 없는(마이그레이션 이전) 행만 건드린다.
7. **편집 잠금(F13)**: `timelines.bump_content_version`을 `status != 'rendering'` 조건부 UPDATE로 바꿨다. 클립·오디오·자막 편집이
   모두 이 함수를 지나므로 렌더 claim과 직렬화된다. 자막 서비스는 쓰기 전에 해당 트랙을 굽는(또는 프로젝트 기본 스타일이면 프로젝트의)
   렌더 중 타임라인을 확인해 409 `RENDER_LOCKED`를 낸다.
8. **reconcile 확장**: (d) 시작된 렌더의 lease 만료 → `failed`(로컬 작업이라 불확실 상태 없음). 시작 전 lease 만료 → 렌더 태스크를
   다시 보내고 lease를 한 번 더 연장(큐 대기가 길어도 실패시키지 않음, 시작 표시가 1회 실행을 보장). 토큰 없는 `rendering`(레거시) → `failed`.
   (e) `queued` 멀티샷이 `RECONCILE_REDISPATCH_AFTER_SEC` 동안 전송되지 않았으면 오케스트레이터를 다시 보낸다.
   `running` 멀티샷 중 자식이 끝났는데 프레임 훅이 유실된 세트는 재집계한다. reconcile은 샷·잡을 직접 만들지 않는다.
9. **멀티샷 1회 fan-out(D9/RH2)**: `run_multishot`의 첫 문장이 claim(`queued → running` 조건부 UPDATE)이고, 같은 트랜잭션에서
   샷 6개·자식 잡 6개·프레임 연결을 만든다. 연결은 `generation_id IS NULL` 조건의 1회 UPDATE이며
   `multishot_frames`의 `UNIQUE(generation_id)`·`UNIQUE(shot_id)`가 뒷받침한다. 자식 디스패치와 SSE는 commit 뒤다.
   중복 전달은 Postgres에서 행 잠금 후 조건을 다시 평가해 0행, SQLite에서는 쓰기 직렬화로 0행이 된다. 트랜잭션 안에서 실패하면
   전부 롤백되고(세트는 `queued`, 자식 없음) 별도 commit으로 세트·프레임을 `failed`로 남겨 결정적 실패를 무한 재전송하지 않는다.

### 결정
1. **보이는 구간으로 큐 자르기(H1)**: 검사 창은 `[0, 출력 길이 − 1프레임)`이다. 큐가 이 창과 1프레임 이상 겹치면 겹친 구간으로 잘라
   검사하고, 픽셀 존재·OCR 모두 그 잘린 구간의 중간 시점을 쓴다. 겹침이 1프레임 미만(출력 끝 뒤 등)인 큐만 빼고 `unverified`에 개수를 남긴다.
2. **길이는 인코딩 probe 하나로(M1)**: `postflight_encoding`의 `measured.duration_sec`을 재사용한다(두 번째 probe 없음).
   자막 트랙이 있는데 길이가 0·불명이면 problem으로 게시하지 않는다.
3. **트랙별 글리프 영역(H2)**: 큐마다 그 큐 하나를 해당 트랙의 해석된 스타일(위치·여백·폰트·외곽선)로 빈 캔버스(출력 크기)에 불투명 흰색으로
   렌더해(`subtitle_render.render_glyph_mask`) 글리프+외곽선 영역을 얻는다(휘도 > `RENDER_BURNIN_MASK_LUMA`, 1px 팽창).
   그 시점에 보이는 다른 트랙 큐의 영역(2px 팽창)은 뺀다. 남은 영역에서 기준본 대비 휘도 차 > `RENDER_BURNIN_PIXEL_DELTA`인 픽셀이
   `max(RENDER_BURNIN_MIN_CHANGED_PX, RENDER_BURNIN_MASK_MIN_FRACTION × 영역 px)` 이상이어야 pass다. 영역이 다른 트랙에 가려
   하한보다 작으면 검증 불가로 fail이다. 같은 밴드 차이를 여러 트랙의 증거로 재사용하지 않는다. B4b 절 결정 4항 "픽셀 존재 검사"의 밴드 기준과 "출력 끝 이후에 시작하는 큐" 문장은 이 절 1~3항으로 대체한다.
   실측(640×360, 회색 배경): 8px 정상 6~11%(46/402, 102/986 px), 32px 정상 24%(646/2696), alpha FF 0.
4. **자막 범위 공통 잠금(H3)**: 큐 교체·스타일 저장·트랙 삭제와 타임라인의 트랙 선택·자막 모드 변경은 같은 트랜잭션의 첫 잠금으로
   프로젝트 행을 잠근다(`subtitles.lock_subtitle_scope`, `SELECT … FOR NO KEY UPDATE`; SQLite는 쓰기 직렬화). 선택 타임라인 조회는
   잠금 뒤에 한다. 먼저 commit된 선택 변경은 편집이 보고(해당 타임라인 bump 또는 렌더 중이면 409), 나중 선택 변경은 편집 commit을 기다린다.
   선택 변경은 렌더 중이면 조건부 bump가 409 `RENDER_LOCKED`로 거절한다. 잠금 순서: **프로젝트 → 타임라인**. render claim은 타임라인 행만 잡는다.
5. **상태 쓰기는 현재 행 조건(H4)**: 이름 변경은 상태를 바꾸지 않는 조건부 UPDATE(`status != 'rendering'`, 0행이면 409)다.
   `done → draft`는 렌더 내용을 바꾼 수정에서만, `WHERE status='done'` 조건부 UPDATE로 한다. 세션이 앞서 읽은 상태를 되쓰지 않는다.
6. **게시도 실패 경계 안(M2)**: `publish_output` 호출이 렌더와 같은 try 안에 있다. 예외는 토큰 CAS로 `failed`를 commit한다.
   `done` commit이 성공하고 응답만 잃은 경우 CAS(`status='rendering'`)가 0행이라 `done`을 덮지 않는다.
7. **멀티샷 세트 집계 직렬화(H5)**: `multishot.aggregate_set`은 세트 행을 잠근 뒤 **모든** 프레임 상태로 집계한다. 프레임 훅은 프레임을 쓴 뒤
   이 함수를 부르고, reconcile `reaggregate`는 terminal 자식을 pending 프레임에 조건부 UPDATE(`status='pending'`)로 반영한 뒤 항상 호출한다.
   집계 SSE(진행·완료)는 commit 뒤에 보낸다. 잠금 순서(B4a-fix 절 3항 확장): 자식 generation → 배치 부모 → Video → Shot → **MultishotFrame → MultishotSet**.
   reconcile은 프레임을 id 순으로 쓴다.
8. **진행 이벤트 순서(M3)**: `run_multishot`의 30%(`frames_queued`) 이벤트를 자식 dispatch 콜백보다 먼저 등록한다(콜백은 등록 순서로 실행).
9. **테스트 DB 격리(R2-C1)**: `tests/conftest.py`는 `DATABASE_URL`을 무조건 SQLite 메모리 URL로 덮어쓰고, DB fixture는 임시 SQLite 파일을 쓴다.
   Postgres는 `TEST_DATABASE_URL`을 명시했을 때만 쓰며, 스키마 초기화 전에 URL의 DB 이름과 접속한 `current_database()`가 모두
   `test`로 끝나는지 확인한다(예: `hiway_test`). 아니면 아무 문장도 실행하지 않고 테스트를 실패시킨다. `make test`도
   `DATABASE_URL`을 SQLite로, `TEST_DATABASE_URL`을 빈 값으로 넘긴다.

### 근거
- 대조 출력("이 트랙만 뺀 렌더")보다 단독 글리프 영역이 싸다(트랙마다 영상 재인코딩 대신 1프레임 lavfi 렌더). 레이아웃은 같은 `_style_line`·

- 버린 대안: 변경 픽셀 하한만 올리기(정상 작은 자막을 거절할 뿐 교차 트랙 오탐은 그대로), 이름 변경을 렌더 중에도 허용(읽기 전용 규칙과 어긋남).

## 추가 결정: 리뷰 보완 (B4a-r2-fix — R2-H1, R2-M1~M4)

### 배경
- 대기 전이(retry·enqueue)가 샷을 잠그지 않았다. retry는 캐시된 샷으로 `_set_shot_generating()`을 불렀고, 샷이 이미
  `frame_generating`이면 UPDATE가 없어 행 잠금도 없었다. 같은 샷의 다른 테이크 A가 terminal 집계를 하면서 R이 아직 commit하지 않은
  B(`failed → queued`)를 `failed`로 읽고 샷을 `frame_done`으로 commit했다. 그 뒤 R이 commit하면 B는 queued인데 샷은 `frame_done`이었다.
  reconcile (g)는 `frame_generating`/`video_generating` 샷만 봐서 고치지 못했다(R2-H1, 영상 retry·`enqueue_video`도 같음).
- 스타일 추출 워커는 `style_extractions → 원장`, cancel·reconcile은 `원장 → style_extractions` 순으로 잠가 Postgres에서
  40P01 교착이 났다(R2-M1).
- 원장이 없는 전역 키트 추출은 after-commit 전송이 실패하면 reconcile이 보지 않아 영구히 queued였다(R2-M2).
- 0014 이전의 실패한 스타일 원장(잡 행 없음)을 retry하면 수락·재전송되지만 워커는 잡 행이 없어 no-op이었다(R2-M3).
- `cancel_job`이 배치 부모를 정할 때 처음 읽은 자식 상태를 썼다. 취소 CAS가 0행(그사이 성공 commit)인 자식은 캐시에 `running`으로 남아
  `[succeeded, canceled]`인데도 부모가 `failed`(집계 규칙)로 남았다(R2-M4).

### 결정
1. **대기 전이도 샷을 잠근다(R2-H1)**: 프레임 테이크의 enqueue(`enqueue_frame`·변형·inpaint·upscale·outpaint)와 retry는
   `generations.mark_frame_shot_pending`, 영상 잡의 `enqueue_video`와 retry는 `videos.mark_video_shot_pending`을 부른다. 둘 다 자식 행(·배치 부모·Video)을
   쓴 뒤 마지막으로 샷을 `SELECT … FOR NO KEY UPDATE`로 잠그고 다시 읽은 다음, 이 트랜잭션에서 보이는 현재 대기 잡으로 결정한다
   ("이미 generating이면 쓰지 않음"을 직렬화 수단으로 쓰지 않는다). 잠금 순서는 B4a-fix 절 3항(자식 → 배치 부모 → Video → Shot) 그대로다.
   따라서 다른 잡의 terminal 재계산은 먼저 commit하면 이 전이가 정착된 샷을 되돌리고, 나중이면 샷 잠금을 기다린 뒤 대기 잡을 본다.
   프레임 쪽은 이미지 job_type의 비배치 테이크만 대기로 센다(영상 잡은 영상 쪽이 다룬다).
2. **reconcile (g) 양방향(R2-H1)**: 기존 "대기 잡 없는 generating 샷 재계산"에 더해, 대기 이미지 테이크가 있는
   `draft|frame_done|frame_approved|failed` 샷은 `frame_generating`으로, 대기 영상 잡이 있는 샷(`video_generating`·`frame_generating` 제외)은
   `video_generating`으로 되돌린다. 같은 헬퍼로 샷을 잠그고 다시 확인한 뒤 쓴다.
3. **스타일 추출 잠금 순서 통일(R2-M1)**: 모든 경로(워커 완료, 크래시 실패 기록, retry, cancel, reconcile)에서
   **원장 generation → `style_extractions` → 스타일 키트**다. 워커는 원장을 먼저 잠근 뒤(`lock_row`) 잡 행을 claim하고, `fail_extract`는
   원장 UPDATE 뒤에 잡 행을 쓴다. cancel·retry·reconcile은 원래 원장을 먼저 쓰고 `on_generation_terminal`/`_retry_dependents`로 잡 행에 간다.
4. **원장 없는 추출 reconcile (h)(R2-M2)**: 대응 원장이 없는 `style_extractions` 중 `RECONCILE_REDISPATCH_AFTER_SEC`보다 오래된 `queued`는
   `q.p1.run_style_extract`로 재전송한다(claim이 1회 실행 보장). `RECONCILE_P1_STUCK_AFTER_SEC`가 지나도 queued인 행(원장 (c)와 같은 기한)과
   생성 후 `LEASE_TTL_SEC`가 지난 `running` 행(claim과 완료가 한 트랜잭션이라 정상 경로에서는 commit되지 않는 상태)은 조건부 UPDATE로
   `failed`(`PROVIDER_ERROR`)다. 프로젝트 키트 행은 원장 경로((b)(c)·terminal 훅)로만 복구해 이중 전송하지 않는다.
5. **잡 행 없는 원장 retry 거절(R2-M3)**: `retry_job`은 쓰기 전에 style_extract 대상의 `style_extractions` 행을 확인하고, 없으면
   400 `VALIDATION_ERROR`(`reason: no_extraction_job_row`, "키트에서 추출을 다시 요청")로 거절한다. 입력 스냅샷을 지어내지 않는다.
   B4a-fix 절 "호환성"의 0014 이전 원장 문장에 이 거절을 더한다.
6. **cancel 부모 판정 재조회(R2-M4)**: `cancel_job`은 배치 부모를 잠근 상태(취소된 자식의 집계에서 이미 잠금)로 자식 상태를 스칼라 조회로
   다시 읽고, 모두 terminal이면 부모를 `canceled`로 둔다(기존 cancel 규칙). 캐시된 자식 상태는 쓰지 않는다.

### 근거
- 샷 잠금은 terminal 쪽과 같은 행·같은 순서라 새 교착 경로가 없다. 대기 전이의 결정은 자기 트랜잭션이 쓴 대기 행을 항상 보므로

## B4-r3 — QC 최신 리포트 총순서 (B4R3-H1), 대기 전이의 stale 해제 조건 (B4R3-M1)

### 결정
1. **QC 리포트 발행 순번(H1)**: `qc_reports.seq`(INTEGER NOT NULL, `UNIQUE(target_type, target_id, seq)`, 마이그레이션 `0015_qc_report_seq`)를
   둔다. `request_qc`는 타임라인 행을 `lock_row`(SELECT … FOR NO KEY UPDATE)로 먼저 잠그고, 행 삽입 시 컬럼 기본값이 같은 대상의
   `max(seq) + 1`을 부여한다. "최신 리포트"(`qc_orchestrator.latest_report` — 렌더 게이트 `assert_render_allowed`와
   `GET /timelines/{id}/qc-latest`가 공유)는 `seq DESC`로 고른다. `created_at`은 표시용이며 순서 판정에 쓰지 않는다.
   기존 행은 대상별 `(created_at, id)` 순으로 백필한다.
2. **stale 해제 조건(M1)**: 프레임 enqueue(`enqueue_frame`·변형·inpaint·upscale·outpaint)는 프롬프트를 조립할 때(멀티패스는 샷을 읽을 때)
   샷의 프롬프트 입력(`generations.FRAME_PROMPT_FIELDS`)과 `frame_stale`을 스냅샷하고, `mark_frame_shot_pending(clear_stale=True,
   prompt_inputs=…)`은 샷을 잠그고 다시 읽은 값이 스냅샷과 같고 그사이 `frame_stale`이 새로 켜지지 않았을 때만 `frame_stale=False`로 쓴다.
   잠금 순서(자식 → 배치 부모 → Video → Shot)는 그대로다. 스냅샷이 없는 retry·reconcile 경로의 동작은 바꾸지 않는다.

### 근거
- SQLite `CURRENT_TIMESTAMP`는 1초 해상도, PG `now()`는 트랜잭션 시작 시각이라 `created_at` 동률이 실제로 생긴다(phase4 게이트 매트릭스의
  간헐적 `stale` 실패와 같은 증상). 타임스탬프 정밀도나 UUID 보조 정렬은 발행 순서를 보장하지 않는다. 타임라인 행 잠금 아래의 max+1은
  타임라인 편집(`bump_content_version`)과도 직렬화되어 `seq`가 클수록 `timeline_content_version`도 작지 않다. UNIQUE 제약은 잠금을
  거치지 않는 삽입이 동률을 만들면 오류로 드러낸다(같은 flush의 여러 행은 실행 컨텍스트 캐시로 구분).
- stale 표시는 "저장된 프롬프트가 현재 샷 입력과 다르다"는 경고이므로, 해제도 "이 잡의 프롬프트가 잠금 시점의 입력과 같다"를 확인한 뒤에만 한다.
  캐릭터 외형 편집처럼 샷 필드를 바꾸지 않는 무효화는 `frame_stale`이 false→true로 바뀐 것으로 감지한다.
- 버린 대안: 전역 autoincrement(SQLite는 PK 외 autoincrement 불가), 동률 시 거절(정상 연속 실행도 막힘), 잠금 뒤 프롬프트 재조립
  (세션 identity map 무효화가 필요하고 비용이 큼).

### 영향
- 코드: `models/qc.py`(`seq`, `_next_report_seq`), `services/qc_orchestrator.py`(`request_qc` 잠금, `latest_report`),
  `services/generations.py`(`FRAME_PROMPT_FIELDS`, `frame_prompt_inputs`, `_stale_resolved_by`).
- 호환성: 0015는 가산적이다. SQLite batch 재생성 시 `ix_qc_target_created`의 `DESC` 표기는 사라지지만 조회에는 영향이 없다.
  retry가 이전 프롬프트로 다시 실행할 때 stale을 해제하는 기존 동작은 이번 범위 밖이다.
- 검증: `tests/test_qc_ordering.py`(동률 pass→fail·pass→pending·v1 warn→v2 fail, 순번·UNIQUE, PG 동시 요청 직렬화),
  `tests/test_job_lifecycle.py`(조립 후 편집 commit 시 stale 유지 — PG, 정상 enqueue 시 해제).

## B4-r4 — legacy 동률 리포트 (B4R4-H1), 이미 stale인 샷의 새 무효화 (B4R4-M1), SQLite 순번 읽기 직렬화 (B4R4-M2)

### 결정
1. **순서 불명 legacy 리포트(H1)**: 0015 백필은 `(created_at, id)` 순번을 주지만, 같은 대상에서 `created_at`이 겹친 legacy 행은 실제 발행
   순서를 알 수 없다. 0015는 그런 행을 모두 `qc_reports.order_ambiguous=true`로 표시하고, `assert_render_allowed`는 최신 리포트가
   ambiguous이면 결과(pass·warn·fail·pending)와 무관하게 409 `QC_FAILED`(reason='stale', `order_ambiguous=true`)로 거부한다 — 새 QC가
   필요하다. pending보다 먼저 검사한다(legacy pending은 끝나지 않을 수 있다). `request_qc`로 생긴 행은 항상 false이므로 새 QC 한 번으로
   해소된다. 동률이 없는 legacy 이력은 표시하지 않고 기존처럼 게이트에 쓴다.
2. **무효화 리비전(M1)**: `shots.frame_stale_rev`(INTEGER NOT NULL DEFAULT 0, 0015)를 둔다. 무효화는 `Shot.mark_frame_stale()` 하나로만
   켜며, 영속 행에서는 SQL 식 `frame_stale_rev + 1`로 올린다(동시 무효화가 같은 값으로 합쳐지지 않음). enqueue 스냅샷은 리비전을 포함하고,
   `_stale_resolved_by`는 샷 필드 비교(B4R3-M1)에 더해 잠금 후 리비전이 스냅샷과 같을 때만 해제한다. 무효화의 UPDATE는 enqueue의
   Shot 잠금(FOR NO KEY UPDATE)과 충돌하므로 잠금 뒤 읽은 리비전은 그 전에 commit된 모든 무효화를 반영한다. 캐릭터 외형 편집
   (`character._mark_dependent_shots_stale`)은 리비전을 올리고 샷을 id 순으로 갱신한다. `scene.update_shot`의 직접 대입은 샷 필드
   비교로 계속 감지되며, 같은 헬퍼로 옮기는 것은 후속 한 줄 변경이다.
3. **SQLite 쓰기 잠금(M2)**: SQLite는 행 잠금이 없어 `lock_row`의 FOR UPDATE가 무시되고, `request_qc`의 `MAX(seq)` 읽기 두 개가 겹치면
   한쪽이 UNIQUE 위반으로 실패했다. SQLite에서 `lock_row`는 먼저 대상 행에 no-op 쓰기(`UPDATE t SET pk = pk WHERE pk = :id`)를 실행해
   트랜잭션의 DB 쓰기 잠금(RESERVED)을 잡는다. 다른 쓰기 트랜잭션은 busy timeout 동안 기다린 뒤 진행하므로 그 뒤의 읽기-쓰기가
   직렬화된다. UNIQUE 제약은 유지한다. PG 경로는 바뀌지 않는다.

### 근거
- 렌더 자격은 "확실히 최신인 리포트가 통과했다"일 때만 준다. 동률 legacy의 UUID 순서는 이력 표시에는 쓸 수 있어도 자격 판정에는 쓸 수 없다.
- bool 비교는 True→True 재무효화를 표현하지 못한다. 단조 증가 리비전은 무효화 횟수를 그대로 드러낸다.
- 버린 대안: 순번 충돌 시 재시도(경합마다 롤백·재조립), SQLite `BEGIN IMMEDIATE` 전역 적용(모든 읽기 전용 트랜잭션까지 쓰기 잠금).

### 영향
- 코드: `db/alembic/versions/0015_qc_report_seq.py`(미배포라 0015를 수정), `models/qc.py`(`order_ambiguous`),
  `models/production.py`(`frame_stale_rev`, `mark_frame_stale`), `services/qc_orchestrator.py`(게이트),
  `services/generations.py`(`lock_row`, `frame_prompt_inputs`, `_stale_resolved_by`), `services/character.py`.
- 호환성: 동률 legacy 이력이 최신인 타임라인은 업그레이드 뒤 첫 렌더 전에 QC를 한 번 더 돌려야 한다. SQLite에서 `lock_row`를 부르는
  트랜잭션은 그 시점부터 쓰기 트랜잭션이 된다(모든 호출처가 이미 쓰기 경로).
- 검증: `tests/test_qc_ordering.py`(실제 0014 스키마에 동률 pass→fail·pass→pending을 commit한 뒤 head로 올려 새 `request_qc` 없이 게이트
  거부, 동률 없는 이력 유지, 새 QC로 해소 — SQLite·PG; 두 연결의 MAX 읽기 barrier → seq 1·2),
  `tests/test_job_lifecycle.py`(이미 stale인 샷에 조립 후 캐릭터 외형 편집 commit → stale 유지 — PG; 리비전 증가).

## B5 — 예산 잠금 순서와 불확실 예약 (계획 D1·D2·D7, RH1)

예산 확인은 그 요청이 잡 행을 넣는 **같은 트랜잭션**에서 프로젝트 행 잠금(`budget_guard.lock_project`, `SELECT … FOR NO KEY UPDATE`;
SQLite는 `lock_row`와 같은 no-op 쓰기, `updated_at` 유지)을 먼저 잡고 committed(지출 + queued/running leaf 잡·pending/uncertain LLM·
`PROVIDER_UNCERTAIN` 실패 행·대기 중 멀티샷 세트·`budget_holds`)를 읽는다. 잠금 순서는 **Project(예산) → generation → 배치 부모 → Video → Shot**
(자막 범위는 기존대로 Project → Timeline)이다. enqueue는 shot.seed 고정 등 첫 행 쓰기 전에, retry는 대상 행을 다시 읽기 전에 프로젝트를 잠근다.
워커 완료·실패, reconcile, cancel, 타임라인·자막 편집은 generation/shot 잠금 뒤에 프로젝트를 잠그지 않는다(해제는 상태 전이만으로 일어나
추가 쓰기가 없다). FOR UPDATE 대신 FOR NO KEY UPDATE를 쓰는 이유: 잡 행 INSERT가 FK로 잡는 KEY SHARE와 충돌하지 않아, 같은 트랜잭션에서
먼저 FK 행을 넣은 두 요청이 서로의 KEY SHARE를 기다리는 교착이 없다. 두 예산 확인끼리는 여전히 충돌해 직렬화된다.
수동 retry는 쓰기 전에 다시 거는 시도 전부의 추정비를 예약 확인하고(초과면 403, 상태 변화 없음), `PROVIDER_UNCERTAIN` 시도는 행이 queued로
돌아간 뒤에도 원래 추정비를 `budget_holds` 행으로 남긴다(자동 해제 없음). LLM 호출은 pending 행을 잠금·확인 아래 먼저 commit하고 잠금을 푼 뒤
외부 호출을 한다. 멱등 키는 `idempotency_records`(UNIQUE method+실경로+key)에 잡·예약과 같은 트랜잭션으로 기록되고, 동일 키 경합의 패자는
롤백(잡 행·after-commit dispatch 소멸) 뒤 승자의 응답을 재생한다. 검증: `tests/test_budget_idempotency.py`(SQLite·PG, 동시성은 PG).

## B5-r2 — 예산 기간 앵커와 멀티샷 fan-out 잠금 (리뷰 B5-H1·H2·M1)

### 결정
- **예산 기간 앵커**: `generations.reserved_at`·`audio_generations.reserved_at`을 둔다. 행을 만들 때와 수동 retry로 다시 큐에 넣을 때마다 현재 시각으로 쓴다. 월 집계(지출·예약 모두)와 프로젝트 카드 월 비용은 `created_at`이 아니라 이 값으로 기간을 판정한다. 지난달에 만든 잡을 이번 달에 retry하면 새 attempt는 이번 달 예약이 되고, 이후 검사에도 남는다.
- **보류 기간**: `budget_holds.period_at`은 보류한 *옛* attempt의 `reserved_at`이다. 지난달의 불확실 청구는 지난달에 남고, 이번 달 retry의 새 예약만 이번 달에 들어간다.
- **멀티샷 fan-out 잠금**: `run_multishot`은 set claim 전에 프로젝트 예산 잠금을 잡는다(잠금 순서 Project → set). 예산 검사는 Generation 행과 queued MultishotSet을 서로 다른 SELECT로 읽는다. 두 SELECT 사이에 queued set → leaf 잡 전환이 commit되면 양쪽 모두 그 예약을 놓친다. 잠금을 공유하면 그 전환이 검사 트랜잭션 도중에 commit될 수 없다.
- 캐릭터 master/sheet 생성도 공통 멱등 helper(`idempotency.run`)를 쓴다. 웹은 클릭마다 새 키를 보낸다.

### 근거
- `created_at` 기준 집계에서는 지난달 failed 잡 둘($6씩)을 이번 달 retry하면 두 번 모두 승인되고 `committed`는 0으로 남았다(리뷰 P01). 원본 생성 시각을 바꾸면 이력이 왜곡되므로 별도 컬럼을 둔다.
- 단일 SQL 스냅샷으로 집계를 다시 쓰는 대안도 있었다. 하지만 멀티샷 단가 계산이 Python 쪽 가격표를 쓰고, 잠금 공유가 더 작은 변경으로 같은 보장을 준다. 같은 테이블 안의 상태 전이(queued→succeeded 등)는 한 SELECT가 한 번만 보므로 이 문제가 없다.

### 영향
- migration 0016에 위 세 컬럼 추가(기존 행 `reserved_at = created_at` 백필).
- 테스트: `test_budget_idempotency.py`의 지난달 retry(이미지·오디오), 보류 기간, PG fan-out 경합, master/sheet 멱등 재생.
