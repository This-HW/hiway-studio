# ADR-0008: 태스크 인자는 대상 행 ID 단일 — `{generation_id}` 고정을 일반화

## 상태
승인 (HW가 2026-09-30에 승인)

## 배경
`docs/PROJECT_ARCHITECTURE.md` §4.7은 태스크 함수 시그니처를
`run_generation(generation_id: str)` — **단일 인자 고정**으로 규정하고,
금지 목록(§15)도 "태스크 인자에 프롬프트·파라미터 원문 → `{generation_id}` 단일,
DB가 진실 공급원"을 명시한다.

그러나 Phase 3·4에서 추가된 태스크는 generation 행이 아닌 다른 행을 대상으로 한다:
- `q.post.render_timeline(timeline_id: str)` — 타임라인 렌더
- `q.post.run_qc(qc_report_id: str)` — QC 리포트 실행

두 태스크 모두 단일 문자열 ID 인자이며 DB를 진실 공급원으로 삼는다는 점에서는
규칙의 취지를 따르지만, "`{generation_id}` 단일"이라는 문자 그대로의 규정과는
충돌한다.

## 결정 (제안)
- 규칙을 일반화한다: **태스크 인자는 그 태스크가 연산하는 대상 행의 ID 1개**이며,
  나머지 파라미터는 DB에서 읽는다 (프롬프트·옵션 원문을 인자로 중복 전달 금지).
- 즉 `{generation_id}`는 생성 잡의 경우일 뿐이며, 렌더는 `{timeline_id}`,
  QC는 `{qc_report_id}`를 인자로 받는다. 셋 다 "단일 ID 인자 + DB 정본" 패턴이다.
- `PROJECT_ARCHITECTURE.md` §4.7의 시그니처 문구와 §15 금지 목록을 이 일반화된
  표현으로 수정한다.

## 근거
- 렌더/QC는 generation 행을 거치지 않는다: 억지로 generation_id를 만들면
  의미 없는 중간 행이 생기고, 반대로 타임라인 ID를 쓰면 행→잡 추적이 직접적이다.
- Celery 태스크 재시작·모니터링 관점에서도 "잡이 어떤 행에 대한 것인지"가
  인자에 드러나는 편이 디버깅에 유리하다.

## 영향
- 코드: 변경 없음 (이미 단일 ID 인자로 구현됨).
- 문서: `docs/PROJECT_ARCHITECTURE.md` §4.7, §15 문구 수정.

## 관련
- D-규칙 "태스크 인자 단일" (ARCHITECTURE §15)
- `services/api/app/tasks/tasks_post.py` (`render_timeline`, `run_qc`)
