# ADR-0012: 샷 레퍼런스 삭제 경로 분리

## 상태
제안

## 배경
`DELETE /api/v1/references/{reference_id}`가 두 라우터에 함께 등록돼 있었다.
캐릭터 레퍼런스 삭제(`routers/characters.py`)와 샷 레퍼런스 삭제(`routers/scenes.py`)다.
FastAPI는 먼저 등록된 라우트로 요청을 보낸다. `main.py`가 characters 라우터를 scenes보다
먼저 등록하므로 샷 레퍼런스 삭제 요청은 캐릭터 레퍼런스 핸들러로 갔고,
`character_references`에 그 id가 없으니 항상 404였다. 웹 보드 화면의 레퍼런스 삭제
버튼(`apps/web/stores/board.ts`)은 이 경로를 호출하므로 실제로 동작한 적이 없다.
교차 감사(99-verdict) C12에서 확인한 결함이다.

## 결정
샷 레퍼런스 삭제는 `DELETE /api/v1/shots/{shot_id}/references/{reference_id}`로 옮긴다.
레퍼런스가 그 샷 소속이 아니면 `NOT_FOUND`다(다른 샷의 레퍼런스, 캐릭터 레퍼런스 id 포함).
`DELETE /api/v1/references/{reference_id}`는 캐릭터 레퍼런스 전용으로 남긴다.

## 근거
- 샷 레퍼런스 조회·추가는 이미 `/shots/{shot_id}/references` 아래에 있다. 삭제도 같은
  자원 경로를 쓰면 대칭이 맞고, 경로만 보고 어느 테이블의 행인지 알 수 있다.
- 경로에 소유 샷이 들어가므로 서비스가 소속을 검사할 수 있다. 다른 샷의 레퍼런스를
  잘못 지우는 일이 생기지 않는다.
- 버린 대안 1: 하나의 `/references/{id}` 핸들러가 두 테이블을 차례로 찾는다. 두 도메인이
  한 핸들러에 묶이고, 두 테이블에서 id가 충돌할 때 동작이 모호하다.
- 버린 대안 2: 캐릭터 쪽 경로를 옮긴다. 캐릭터 화면과 시트 화면이 그 경로로
  수정(PATCH)과 삭제를 모두 하고 있고 그쪽은 정상 동작하므로, 고장 난 쪽만 옮기는 편이
  변경 범위가 작다.

## 영향
- 코드: `routers/scenes.py`(경로), `services/scene.py`(`delete_reference(db, shot_id, reference_id)`
  소속 검사), `apps/web/stores/board.ts`(호출 경로).
- 테스트: `tests/test_web_contract.py`가 (method, path) 중복 0건과 샷 경로의 204/404를 고정한다.
- 문서: P0_SCREENS.md 보드 화면 API 표에 이 경로를 추가했다. 시스템 설계서 §8.1의
  레퍼런스 삭제 행을 고칠 때 이 ADR을 근거로 쓴다(설계서는 공개 레포 밖에 있다).
- 호환성: 옛 샷 레퍼런스 삭제 경로는 원래부터 동작하지 않았다(항상 404). 1인 로컬
  도구라 외부 클라이언트가 없으므로 깨지는 호출은 없다.
