# ADR-0009: API 경로 4건의 설계서 불일치 해소

## 상태
승인 (HW가 2026-09-30에 승인)

## 배경
P0 검수(설계서 §8.1 전수 대조)에서 구현된 경로 4건이 설계서와 다르다는 것이
발견됐다. 웹 클라이언트는 이미 구현 경로를 사용 중이며 동작은 검증됐다.
되돌리면 웹 클라이언트의 breaking change가 발생한다.

| # | 설계서 §8.1 | 구현 (실제 동작) |
|---|---|---|
| 1 | `POST /shots/reorder` | `POST /scenes/{scene_id}/shots/reorder` |
| 2 | `POST /projects/{id}/subtitle-tracks/generate` | `POST /subtitle-tracks/{track_id}/generate` |
| 3 | `GET /costs/summary` (`?project_id=`) | `GET /projects/{project_id}/costs/summary` |
| 4 | `DELETE /jobs/{id}` (취소) | `POST /jobs/{job_id}/cancel` |

## 결정
구현 경로를 정본으로 유지하고, 시스템 설계서 §8.1의 4행을 구현에 맞게
고친다. 코드는 바꾸지 않는다.

## 근거
- 1·2·3은 리소스 스코프를 경로에 명시하는 형태라 설계서보다 RESTful하다.
  reorder는 씬 내 순서 변경이므로 씬 하위가 맞고, 자막 생성은 트랙 하위가,
  비용 집계는 프로젝트 하위가 맞다.
- 4는 "취소"가 액션(action)이므로 `DELETE`보다 `POST .../cancel`이 관례에
  맞다. (GitHub Actions의 cancel-workflow 등도 POST.)
- 버린 대안: 설계서대로 코드를 되돌리기 — 웹 클라이언트 4곳 수정 +
  이미 검증된 플로우 재검증이 필요해서 비용만 들고 얻는 게 없다.

## 영향
- 코드: 변경 없음.
- 문서: 시스템 설계서 §8.1 4행 수정. P0_SCREENS.md의 API 표기는 구현
  경로와 일치하므로 변경 없음.
- 호환성: 외부 클라이언트가 없으므로(1인 로컬) breaking change 없음.

## 관련
- 시스템 설계서 §8.1, P0 검수 리포트 (2026-09-30)
