# ADR-0006: Phase 3 렌더는 QC 게이트 없이 동작, QC 연결은 Phase 4에서

## 상태
승인 (HW가 2026-09-30에 승인)

## 배경
설계서 §8.1의 `POST /timelines/{id}/render`는 "QC `fail`이면 409, `warn`이면 `ignore_warnings=true` 필요"를 명시한다.
그러나 QC(routers/qc, services/qc_orchestrator)는 Phase 4 범위이며 Phase 3 시점에는 존재하지 않는다.

## 결정 (제안)
- Phase 3의 `request_render`는 QC 리포트 존재 여부를 검사하지 않는다. `ignore_warnings` 파라미터는 받되 무시한다(Phase 4에서 의미 부여).
- Phase 4에서 `services/qc_orchestrator.py`가 생기면 `request_render`에 게이트를 연결한다: 최신 리포트 `overall='fail'` → 409 QC_FAILED, `'warn'` + `ignore_warnings` 미지정 → 409 QC_FAILED(details.reason='warnings_not_ignored').
- 렌더 잡은 `q.post` 큐에서 실행한다 (`render_timeline` 태스크). 렌더는 후처리(post) 성격이며, 큐는 4개로 고정한다(ARCHITECTURE §8).
- 재렌더 시 기존 `output.mp4`는 덮어쓰지 않고 `output_{timestamp}.mp4`로 아카이브한다. `output.mp4`는 항상 최신 렌더를 가리키고, `timelines.output_path`는 단일 값을 유지한다. (불변식 "성공 산출물 덮어쓰기 금지"와 "타임라인 수정 후 재렌더" 흐름을 양립시키기 위함.)

## 근거
- Phase 3 완료 조건("타임라인에서 mp4 1개 출력")은 QC를 요구하지 않는다.
- 큐를 새로 만들지 않고 기존 `q.post`를 쓰는 것이 아키텍처의 "큐 4개 고정" 규칙과 일치한다.

## 영향
- 코드: `services/render.py` (Phase 3), `services/qc_orchestrator.py` (Phase 4).
- 문서: `docs/P0_SCREENS.md` §8의 "QC 상태 표시"는 Phase 4에서 활성화된다.

## 관련
- 시스템 설계서 §8.1 (`POST /timelines/{id}/render`), F-14, P0_SCREENS §8/§9
